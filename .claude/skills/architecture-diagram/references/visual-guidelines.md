# Architecture Diagram Visual Guidelines

This document defines the visual standards for architecture diagrams generated by the `architecture-diagram` skill.

The goal is to produce diagrams that resemble professionally designed Figma, Lucidchart, Excalidraw, Eraser, or cloud-architecture presentation assets rather than automatically generated graph diagrams.

## 1. Core visual principles

Every diagram must prioritise:

1. Architectural correctness
2. Readability
3. Clear hierarchy
4. Consistent visual language
5. Minimal connector crossings
6. Useful interaction
7. Presentation-quality appearance

A diagram must help the reader understand the system without requiring them to read the source code.

Avoid visual decoration that does not communicate architectural meaning.

## 2. Canvas

Use a spacious canvas with sufficient padding around all architecture groups.

Recommended defaults:

```ts
const canvasDefaults = {
  minWidth: 1440,
  minHeight: 900,
  outerPadding: 64,
  groupPadding: 32,
  nodeGapX: 48,
  nodeGapY: 32,
};
```

The rendered diagram should support:

* Zoom
* Pan
* Fit to screen
* Reset view
* Full-screen presentation
* Responsive viewport resizing

The canvas should not force the entire architecture to shrink until labels become unreadable.

## 3. Diagram direction

Choose one dominant reading direction.

Use left-to-right when showing:

* User requests
* API processing
* Event processing
* Authentication
* CI/CD delivery
* Incident ingestion
* Data pipelines

Use top-to-bottom when showing:

* Layered architecture
* Application, platform and infrastructure layers
* Control plane versus data plane
* Organisation or responsibility hierarchy

Use columns when showing:

* Multiple Kubernetes clusters
* Multiple cloud accounts or projects
* Environments such as development, staging and production
* Active and disaster-recovery regions

Use nested boundaries when showing:

* Cloud accounts
* Projects
* Regions
* VPCs
* Kubernetes clusters
* Namespaces
* Trust zones
* Tenant boundaries

Do not mix multiple unrelated reading directions on the same canvas.

## 4. Architecture hierarchy

The visual hierarchy should normally be:

```text
Canvas
  └── Environment or cloud boundary
        └── Region or network boundary
              └── Kubernetes cluster or platform boundary
                    └── Namespace or application domain
                          └── Component node
```

Not every level must be used.

Only create boundaries that help answer the architecture question.

Avoid deeply nested boxes when they do not add architectural meaning.

## 5. Node categories

Use a consistent category system.

Recommended categories:

```ts
type NodeCategory =
  | "actor"
  | "client"
  | "edge"
  | "gateway"
  | "application"
  | "worker"
  | "platform"
  | "security"
  | "database"
  | "cache"
  | "messaging"
  | "storage"
  | "observability"
  | "cicd"
  | "external";
```

Suggested semantic treatment:

| Category      | Meaning                                         | Suggested treatment                |
| ------------- | ----------------------------------------------- | ---------------------------------- |
| Actor         | Human or organisational actor                   | Compact neutral card               |
| Client        | Browser, mobile app, CLI or agent               | Light client card                  |
| Edge          | CDN, load balancer, ingress or proxy            | Strong border                      |
| Gateway       | API gateway, ingress gateway or service gateway | Accent header                      |
| Application   | API, UI, backend service or domain service      | Primary service card               |
| Worker        | Background or event-processing service          | Service card with worker indicator |
| Platform      | Kubernetes or shared runtime capability         | Platform-style card                |
| Security      | Identity, secrets, policy or authorization      | Shield indicator                   |
| Database      | Relational, document or analytical database     | Database glyph                     |
| Cache         | Redis or distributed cache                      | Compact storage card               |
| Messaging     | Queue, stream or event bus                      | Horizontal bus or broker card      |
| Storage       | Object, file or block storage                   | Storage glyph                      |
| Observability | Metrics, logs, traces or alerting               | Telemetry indicator                |
| CI/CD         | Build, deployment or GitOps system              | Delivery indicator                 |
| External      | Third-party or external dependency              | Dashed outer border                |

Do not use colour alone to distinguish categories. Also use labels, icons or shape differences.

## 6. Node dimensions

Use predictable node sizes.

Recommended defaults:

```ts
const nodeSizes = {
  small: {
    width: 160,
    height: 72,
  },
  medium: {
    width: 210,
    height: 96,
  },
  large: {
    width: 260,
    height: 128,
  },
  datastore: {
    width: 190,
    height: 100,
  },
  messaging: {
    width: 240,
    height: 88,
  },
};
```

A normal node should contain:

* Icon
* Component name
* Short responsibility
* Technology label
* Optional environment badge
* Optional confidence indicator

Do not place implementation paragraphs inside nodes.

Move detailed information into the node details panel.

## 7. Node content

A typical node should display:

```text
[Icon] Component name
Short responsibility
Technology · Environment
```

Recommended text limits:

* Component name: 1–3 lines
* Responsibility: 1–2 short lines
* Technology metadata: 1 line
* Maximum visible words inside a normal node: approximately 18

Use tooltips or details panels for longer information.

## 8. Typography

Use the existing application typography when available.

Otherwise prefer a modern system font stack:

```css
font-family:
  Inter,
  ui-sans-serif,
  system-ui,
  -apple-system,
  BlinkMacSystemFont,
  "Segoe UI",
  sans-serif;
```

Recommended sizes:

```ts
const typography = {
  canvasTitle: 24,
  canvasSubtitle: 14,
  groupTitle: 14,
  groupMetadata: 11,
  nodeTitle: 14,
  nodeDescription: 11,
  nodeMetadata: 10,
  edgeLabel: 10,
  badge: 9,
};
```

Avoid text smaller than 9 pixels in the rendered SVG.

## 9. Colour usage

Use restrained semantic colour.

Colour should indicate component category or architectural role, not create decoration.

Recommended CSS-variable approach:

```css
:root {
  --diagram-background: #f8fafc;
  --diagram-surface: #ffffff;
  --diagram-border: #cbd5e1;
  --diagram-text: #0f172a;
  --diagram-muted-text: #475569;

  --diagram-actor: #64748b;
  --diagram-edge: #2563eb;
  --diagram-application: #4f46e5;
  --diagram-platform: #0891b2;
  --diagram-security: #7c3aed;
  --diagram-database: #0284c7;
  --diagram-messaging: #d97706;
  --diagram-observability: #059669;
  --diagram-cicd: #db2777;
  --diagram-external: #64748b;

  --diagram-confirmed: #16a34a;
  --diagram-inferred: #ca8a04;
  --diagram-unverified: #dc2626;
}
```

Dark mode should use equivalent semantic tokens rather than hardcoded duplicate styles.

Do not assign each service an unrelated colour.

## 10. Boundaries

Boundary cards should clearly communicate ownership and runtime location.

A boundary should include:

* Boundary title
* Boundary type
* Optional environment label
* Optional region or network metadata
* Optional trust classification

Examples:

```text
Google Cloud — Management Project
AWS Account — Production
Kubernetes Cluster — alarmify-dev
Namespace — incident-platform
Trust Zone — Internal Services
```

Boundary treatment:

* Rounded corners
* Subtle background tint
* Medium border
* Header label attached to the upper edge
* Sufficient internal padding
* No heavy shadows

Nested boundaries must remain visually distinguishable.

Use progressively lighter backgrounds for deeper nesting.

## 11. Connectors

Connectors must communicate architectural meaning.

Every important connector should indicate:

* Direction
* Source
* Destination
* Communication type
* Protocol or event name where relevant

Recommended connection categories:

```ts
type ConnectionType =
  | "synchronous"
  | "asynchronous"
  | "authentication"
  | "control-plane"
  | "telemetry"
  | "replication"
  | "administrative"
  | "fallback"
  | "unknown";
```

Suggested connector semantics:

| Type           | Visual treatment                    |
| -------------- | ----------------------------------- |
| Synchronous    | Solid line with arrow               |
| Asynchronous   | Dashed line with arrow              |
| Authentication | Solid line with security marker     |
| Control plane  | Fine dotted or dash-dot line        |
| Telemetry      | Thin dashed line                    |
| Replication    | Double-line or labelled solid line  |
| Administrative | Neutral fine line                   |
| Fallback       | Dashed line with fallback label     |
| Unknown        | Dashed line with question indicator |

Use different treatments through stroke patterns and labels, not colour alone.

## 12. Connector routing

Preferred routing order:

1. Orthogonal routing
2. Smooth rounded orthogonal routing
3. Curved routing only where it improves readability
4. Straight routing for short direct connections

Connectors should:

* Attach to defined node ports
* Avoid running through nodes
* Avoid running through group titles
* Avoid crossing labels
* Avoid unnecessary bends
* Use consistent corner radius
* Keep arrowheads visible
* Remain readable at normal zoom

When several edges share a route, use:

* API gateway
* Event bus
* Shared broker
* Telemetry collector
* Connection lane
* Aggregation node

Do not draw ten nearly identical lines across the entire diagram when one labelled bus would be clearer.

## 13. Ports

Nodes should expose directional ports:

```ts
type PortSide = "top" | "right" | "bottom" | "left";
```

Recommended use:

* Incoming user traffic: left
* Outgoing request flow: right
* Control-plane traffic: top
* Storage or platform dependency: bottom
* Telemetry export: bottom or dedicated telemetry port

Ports may remain visually hidden until the node is selected, but connector attachment points must be deterministic.

## 14. Edge labels

Use short labels such as:

```text
HTTPS
gRPC
OIDC
SQL
NATS event
Kafka topic
OTLP
Prometheus scrape
Git sync
Argo CD reconcile
DNS
mTLS
```

Avoid labels such as:

```text
This service sends an HTTPS request containing tenant information
```

Move verbose descriptions to the edge details panel.

Place labels near the middle of an edge without overlapping other connectors.

## 15. Icons

Prefer existing repository icon libraries.

Suitable sources include:

* Lucide
* Heroicons
* Simple Icons
* Cloud-provider icon packages
* Existing product icon components

Icons should identify technology or role.

Do not mix many unrelated icon styles.

Do not download external assets at runtime unless the project already has a supported asset pipeline.

For cloud provider diagrams, official icons may be used when already available in the repository.

Otherwise use clean generic icons with explicit text labels.

## 16. Confidence indicators

Architecture evidence should be visible.

Recommended confidence states:

```ts
type ConfidenceLevel =
  | "confirmed"
  | "strongly-inferred"
  | "planned"
  | "unverified"
  | "contradictory";
```

Suggested treatment:

| Confidence        | Treatment                                   |
| ----------------- | ------------------------------------------- |
| Confirmed         | Normal node or edge                         |
| Strongly inferred | Small amber indicator                       |
| Planned           | Dashed outline with planned badge           |
| Unverified        | Dashed outline with question badge          |
| Contradictory     | Warning badge and details-panel explanation |

Confidence indicators must not dominate the diagram.

## 17. Selected and hover states

On node hover:

* Increase border emphasis
* Show a concise tooltip
* Highlight direct relationships
* Keep unrelated nodes visible

On node selection:

* Highlight incoming edges
* Highlight outgoing edges
* Dim unrelated components
* Open the details panel
* Preserve the diagram viewport

Use subtle transitions.

Avoid distracting continuous animations.

## 18. Details panel

The details panel should show:

```text
Component
Responsibility
Category
Technology
Runtime location
Environment
Repository
Relevant source files
Incoming dependencies
Outgoing dependencies
Protocols
Authentication
Confidence
Risks
Open questions
```

The panel should be scrollable and should not cover the entire diagram on desktop.

Recommended desktop width:

```ts
const detailsPanelWidth = 380;
```

On smaller screens, use a bottom sheet or full-width drawer.

## 19. Toolbar

Recommended controls:

* Search
* Zoom in
* Zoom out
* Fit view
* Reset
* Toggle labels
* Filter by environment
* Filter by category
* Filter by connection type
* Toggle optional infrastructure
* Full screen
* Export SVG
* Export PNG

Group related actions.

Do not place every control as an equally prominent button.

## 20. Legend

The legend should explain:

* Node categories
* Edge styles
* Confidence states
* Boundary meaning

Keep the legend collapsed by default when the canvas is small.

Do not repeat information already self-evident from node labels.

## 21. Responsive behaviour

Desktop is the primary diagram experience.

For smaller screens:

* Preserve zoom and pan
* Allow the details panel to become a drawer
* Collapse the toolbar
* Avoid rearranging nodes automatically on every viewport resize
* Keep deterministic diagram coordinates
* Allow horizontal exploration

Do not compress the complete architecture into a narrow single-column layout unless it is explicitly a mobile-focused diagram.

## 22. Accessibility

Provide:

* Keyboard-focusable nodes
* Clear focus rings
* Accessible button labels
* Tooltips that do not require a mouse
* Sufficient text contrast
* Non-colour indicators for semantics
* Reduced-motion support
* Descriptive SVG title and description
* Screen-reader labels for important nodes

Example:

```tsx
<svg
  role="img"
  aria-labelledby="architecture-title architecture-description"
>
  <title id="architecture-title">
    Alarmify incident-processing architecture
  </title>

  <desc id="architecture-description">
    Architecture showing alert ingestion, event processing, persistence,
    notifications and observability across Kubernetes clusters.
  </desc>
</svg>
```

## 23. Export quality

SVG export should preserve:

* Fonts or font fallbacks
* Node styles
* Connector labels
* Arrowheads
* Icons
* Boundaries
* Legend when requested

PNG export should:

* Support an increased pixel ratio
* Use the current theme
* Include the complete diagram bounds
* Avoid clipping shadows or labels

Do not rely on screenshots of only the visible viewport.

## 24. Large architecture handling

When the diagram exceeds approximately 25–35 meaningful nodes, consider splitting it.

Recommended split:

```text
View 1: Executive context
View 2: Application and data flow
View 3: Infrastructure and deployment
View 4: Security and authentication
View 5: Observability and operations
```

A focused diagram is preferable to one enormous unreadable graph.

## 25. Quality checklist

Before completing the task, verify:

* No overlapping nodes
* No clipped text
* No connectors through nodes
* No hidden arrowheads
* No unreadable edge labels
* No unexplained colours
* No inconsistent node sizes
* No random spacing
* No meaningless boundaries
* No unsupported architecture claims
* No Mermaid or diagram DSL
* Diagram remains understandable at normal zoom
* Light and dark modes remain readable
* Selected states work
* Filters work
* Export works
* Details panel contains evidence
